# V7.2.0 — GPU for large-scale SRAM: which half do we ship to the GPU?

**Status:** plan only, no behaviour change. Branch `v720-gpu-scaling-plan`.

**The question.** For large-scale SRAM work, do we ship the **NN compact model**
to the GPU, or the **circuit solver**? This document answers it with a measured
scaling profile rather than intuition, and routes the work that follows.

**The answer, up front:**

> **Ship the NN to the GPU. Do not ship the solver.** The linear solve is
> **0.55 %** of an SRAM-array run; the NN forward+Jacobian is **~48 %**.
>
> But the GPU **on its own buys nothing today — measured, not predicted.**
> Running a 16×16 array through the existing GPU path gives 12.11 s vs 11.21 s
> on CPU, and an 8×8 array is **2.2× slower** on the GPU. The GEMM does get
> 2.4× faster; the per-device Python around it gets 2.6× *slower*, because
> every MOSFET's result is read back with an individual `.tolist()` — one
> device sync each — and every MOSFET's input is re-marshalled with individual
> kernel launches.
>
> **47 % of the run is per-device Python that no GPU can touch.** So the
> deliverable is *not* "move the model to CUDA"; it is **delete the per-device
> Python first (Phase 2), then move the model to CUDA (Phase 3)**. Together
> ~7–10×. Phase 2 alone is worth ~1.7× and needs no GPU and no re-gate. Phase 3
> alone is worth ~1.0×.

---

## 1. Measurement setup

6T SRAM array, R×C cells, generated hierarchically (`.subckt sraminv` + access
pair), DirectNet `large` (907,565 params) TSMC5 N/P, `.op` with `.ic` on every
cell. Gate configuration: `CUDA_VISIBLE_DEVICES="" OMP_NUM_THREADS=1
MKL_NUM_THREADS=1`, torch 1 thread. Host: 192-core CPU, 3× RTX 4090 (shared,
50–90 % busy from other users — GPU numbers are therefore *pessimistic*).

Every number below is measured. Scripts in the session scratchpad
(`gen_sram_array.py`, `prof_scale.py`, `prof_split.py`, `bench_nn_batch.py`,
`bench_spsolve.py`).

Node count is `2·cells + rows + 2·cols + 1` — two storage nodes per cell, the
inverter internals being subckt ports that flatten onto `q`/`qb`.

## 2. Where the time actually goes

`.op` on the array, CPU, one thread. `nn` = `_batch_eval_nn_mosfets`,
`stamp` = the per-device `_stamp_mosfet_dc` loop, `spsolve` = the MNA solve.

| array | devices | nodes | **solve** | nn | stamp | spsolve | tocsr | other | parse |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 2×2 | 24 | 15 | 0.24 s | 0.17 | 0.04 | 0.01 | 0.00 | 0.02 | — |
| 4×4 | 96 | 45 | 0.49 s | 0.33 | 0.12 | 0.01 | 0.00 | 0.03 | 0.4 s |
| 8×8 | 384 | 153 | 1.89 s | 1.22 | 0.52 | 0.04 | 0.00 | 0.10 | 2.1 s |
| 16×16 | 1536 | 561 | 8.25 s | 5.33 | 2.52 | 0.05 | 0.01 | 0.34 | 14.7 s |
| 32×32 | 6144 | 2145 | **40.38 s** | 26.68 | 11.55 | **0.22** | 0.03 | 1.89 | 44.4 s |

Three facts fall out:

1. **Everything is linear in device count.** The number of linear solves is
   *constant* at 41 across all five sizes — that is the 20-step source-stepping
   schedule at ~2 NR iterations per step, not circuit difficulty — so cost is
   `O(devices)`, the good case.
   **Caveat:** this is measured on `.op` with `.ic` on every cell, which is the
   benign case — every latch is told which state to sit in. A read/write
   transient, or an array without `.ic`, can converge differently, and the
   iteration count is then no longer guaranteed size-independent. Phase 0 of
   §7 should confirm this before the linearity claim is leaned on.
2. **The linear solve is noise: 0.22 s of 40.38 s = 0.55 %.** It is the
   *smallest* line item, smaller than the untracked `other`.
3. **Parse costs as much as the solve** (44 s vs 40 s at 6144 devices). See
   §6 — this is a bug, not a scaling law.

### 2.1 Splitting the NN cost: tensor vs Python

`batch_eval` is not all tensor work. Every device's result goes through
`_unpack_eval` — 13 scalar `_denorm` calls, 3–8 `_denorm_deriv` calls,
`_guard_gds`, and the branchy `_apply_vds_correction` — all scalar Python,
one call per device per NR iteration:

| array | devices | batch_eval | tensor (GEMM+autograd) | Python tail | µs per unpack |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 4×4 | 96 | 0.49 s | 0.41 s (84.5 %) | 0.08 s (15.5 %) | 19.2 |
| 8×8 | 384 | 1.89 s | 1.49 s (78.9 %) | 0.40 s (21.1 %) | 25.4 |
| 16×16 | 1536 | 7.51 s | 5.50 s (73.1 %) | 2.02 s (26.9 %) | 32.1 |

The tail's share **grows** with array size (15.5 → 26.9 %). Applying the 16×16
split to the 32×32 run gives the true budget:

| bucket | 32×32 time | share | GPU-addressable? |
| --- | ---: | ---: | --- |
| NN tensor (forward + autograd) | 19.5 s | **48 %** | **yes** |
| NN Python tail (`_unpack_eval`) | 7.2 s | 18 % | no — vectorise |
| Stamping loop (`_stamp_mosfet_dc`) | 11.6 s | 29 % | no — vectorise |
| `other` (NR bookkeeping, residual) | 1.9 s | 5 % | partly |
| **MNA solve (`spsolve` + `tocsr`)** | **0.25 s** | **0.6 %** | yes, and pointless |

**47 % of the run is per-device Python that no GPU can touch.**

## 3. Option A — ship the NN to the GPU

### 3.1 The shape is already right

`batch_eval` groups devices by shared `nn.Module` identity, and an SRAM array
resolves to exactly **two** checkpoints (tsmc5 NMOS + PMOS) no matter how big
it gets. A 32×32 array is two batched calls of 4096 and 2048 rows per NR
iteration — the ideal GPU shape, and it already exists.

`_get_nn_device()` already returns `cuda` when visible, so the path is
*latent*: it runs today if you unset `CUDA_VISIBLE_DEVICES`. It is not,
however, *effective* — §3.3 measures it at **zero net gain, and a 2.2× loss on
smaller arrays**. Note the accuracy implication of "latent": any run that does
not pin `CUDA_VISIBLE_DEVICES=""` is *already* silently taking the perturbing
GPU path. The gates pin it; ad-hoc runs may not.

### 3.2 Measured per-device cost vs batch size

DirectNet-large, DC path (1 forward + 1 backward) and transient path
(1 forward + 3 backwards), RTX 4090 (contended):

| batch N | DC total | DC µs/device | TRAN total | TRAN µs/device |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 0.76 ms | 762 | 2.40 ms | 2402 |
| 96 | 1.02 ms | 10.6 | 3.31 ms | 34.5 |
| 384 | 1.18 ms | 3.06 | 1.90 ms | 4.94 |
| 1536 | 2.41 ms | 1.57 | 4.24 ms | 2.76 |
| 6144 | 1.57 ms | 0.26 | 7.76 ms | 1.26 |
| 24576 | 10.0 ms | 0.41 | 15.3 ms | 0.62 |
| 98304 | 24.7 ms | 0.25 | 44.4 ms | 0.45 |

Per-device cost collapses **~3000×** from batch 1 to batch 98k. At batch 1 the
GPU is *no better than the CPU* (762 µs vs the 784 µs CPU figure from
`docs/plans/2026-07-25-v700-nn-perf.md`) — kernel-launch bound. The entire
value of a GPU port is in the batching, which the SRAM array supplies for free.

### 3.2b The same sweep on CPU — the contrast that matters

Same harness, CPU, one thread:

| batch N | DC µs/device **CPU** | DC µs/device **GPU** | ratio |
| ---: | ---: | ---: | ---: |
| 1 | 903 | 762 | 1.2× |
| 96 | 52.7 | 10.6 | 5.0× |
| 384 | 41.4 | 3.06 | 13.5× |
| 1536 | 292 | 1.57 | 186× |
| 6144 | 344 | 0.26 | 1300× |

**The CPU stops amortising at ~384 rows and then gets worse; the GPU keeps
improving all the way to 98k.** That divergence is the entire technical case for
the GPU, and it is the one property of these two curves that is robust to the
measurement noise.

> Treat the CPU N≥1536 rows as soft. They disagree with the in-situ profile
> (§2 implies ~77 µs/device at 6144) by ~4×, on a 192-core box shared with
> other users and with my own profiling runs. The turnover is real — activation
> matrices outgrow cache — but its magnitude here is inflated by contention.
> **§2 is the number of record for CPU cost**; this table is for the *shape*.

Cross-check on the physics: the CPU spends 651 ms per NR iteration on 6144
devices = 33 GFLOP at ~40 GFLOP/s, i.e. single-core **FLOP-bound** at this
batch size. This is a genuine regime change from the V7.0.0 finding — at batch
1 the NN was *bandwidth*-bound on the weights (3.6 MB streamed 4×), and the
whole V7.0.x lever set (charge-skip, fused Jacobian, AR cache) was aimed at
reducing weight streams. At SRAM batch sizes the weights are streamed once and
amortised over thousands of rows, so the cost is arithmetic. **The V7.0.x
conclusions do not transfer to this regime, and neither do its levers.**

### 3.3 The blocker: per-device host readback — **measured, not predicted**

`batch_eval` computes on the GPU, then hands `out[i]`, `grad_id[i]` to
`_unpack_eval` **one device at a time**, and `_unpack_eval` calls `.tolist()`
on those slices. On CUDA that is **one device→host synchronisation per MOSFET
per NR iteration**.

Running the array through the latent GPU path today (`CUDA_VISIBLE_DEVICES=1`,
everything else unchanged) confirms the consequence exactly:

| array | solve CPU | solve **GPU** | tensor CPU→GPU | tail CPU→GPU | µs/unpack CPU→GPU |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 8×8 (384 dev) | 2.65 s | **5.82 s** (2.2× *slower*) | 1.49 → 2.43 s | 0.40 → 1.73 s | 25.4 → **110.0** |
| 16×16 (1536 dev) | 11.21 s | **12.11 s** (1.08× slower) | 5.50 → **2.27 s** | 2.02 → **5.32 s** | 32.1 → **84.5** |

Read the 16×16 row carefully — it is the whole argument in one line. The GPU
**did** do its job on the tensor work: 5.50 s → 2.27 s, a 2.4× win. But the
Python tail simultaneously went 2.02 s → 5.32 s, a 2.6× *loss*, because every
one of the 62,976 `_unpack_eval` calls now blocks on a device sync. The two
cancel: `batch_eval` 7.51 s → 7.59 s. **Net gain from switching on the GPU
today: zero, and negative on smaller arrays.**

The tail's cost per call nearly quadruples (32 → 85 µs) even though it executes
the identical scalar arithmetic. That gap is pure synchronisation latency.

### 3.3b The mirror-image blocker on the *input* side

`batch_eval` also assembles its input per device, every NR iteration:

```python
v_raw = torch.tensor(raw_v[key], ..., device=ref._device)  # H2D from a Python list
x_g   = torch.stack([m._geo_norm_t for m in devs], dim=0)  # N separate device tensors
tech  = torch.cat([m._tech_code_tensor for m in devs], dim=0)
```

`_geo_norm_t` and `_tech_code_tensor` are **per-device tensors already resident
on the GPU**, so the stack/cat are N tiny device-to-device kernel launches.
Measured against the batched equivalent (stack once at construction, reuse):

| N | per-device marshalling | batched | ratio |
| ---: | ---: | ---: | ---: |
| 384 | 0.457 ms | 0.020 ms | 23× |
| 1536 | 2.227 ms | 0.012 ms | **185×** |
| 6144 | 6.148 ms | 0.016 ms | **384×** |

The geometry and tech-code rows are **immutable for the lifetime of the
device** — they never change between NR iterations. Stacking them once per
group at construction and caching the result removes this entirely. This is a
pure-waste fix, independent of GPU-vs-CPU.

### 3.3c What this means for the port

The GPU port is not "set the device". It is four separate changes:

- **cache the stacked geometry/tech-code** per group (§3.3b) — immutable data,
  currently re-stacked every iteration;
- build the voltage batch on-device in one op, not from a per-device Python list;
- run forward + autograd batched (already done);
- **one** D2H transfer of the whole `(N, 13)` result + Jacobians, then
  vectorise the denorm/guard/Vds-correction tail over the batch (§3.3).

The last is Phase 2a, and it is the precondition — not an optimisation — for
the GPU being worth anything at all.

### 3.3d Caveat: the GPU numbers were taken on a contended device

All three GPUs were 50–90 % busy with other users' jobs throughout. GPU timings
here are therefore **pessimistic and noisy** — visible in §3.2 as the
non-monotonic 6144 → 24576 row. The 2.27 s tensor bucket in §3.3 is an upper
bound; the §3.2 microbenchmark (~3.6 ms/iteration ≈ 0.15 s for the whole 16×16
solve) is the idle-GPU floor. The gap between them is queueing, not arithmetic.

The conclusions that do **not** depend on GPU contention, and which carry the
recommendation, are all CPU-side or launch-count-side measurements: the 0.55 %
solver share (§2), the 47 % per-device-Python share (§2.1), and the 23–384×
marshalling ratio (§3.3b).

So the GPU port is not "set the device" — it is:

- build the input batch on-device (no per-device Python list → tensor),
- run forward + autograd batched (already done),
- **one** D2H transfer of the whole `(N, 13)` result + Jacobians,
- vectorise the denorm/guard/Vds-correction tail over the batch.

The last item is Option C, and it is what makes Option A pay.

### 3.4 Amdahl, honestly

Taking the 32×32 budget from §2.1. GPU tensor time is bracketed at 0.2–2.0 s
(§3.3d: microbenchmark floor vs contended measurement); the table uses the
optimistic end, and the pessimistic end is given where it changes the verdict.

| scenario | 32×32 solve | speedup |
| --- | ---: | ---: |
| today (CPU, 1 thread) | 40.4 s | 1.0× |
| **A: GPU tensor only, Python untouched** | *no gain* — §3.3 measures it | **~1.0×** |
| A′: GPU tensor, counting tensor work alone | 21.1 s | 1.9× *ceiling* |
| **B: infinitely fast solver** | 40.2 s | **1.005×** |
| D: vectorise Python only, no GPU | 23.5 s | 1.7× |
| **C: GPU tensor + vectorised Python** | 4.2–6.0 s | **~7–10×** |

Row A is the one to internalise: the 1.9× is a *ceiling* that assumes the
Python tail is free, and §3.3 shows empirically that on GPU it is not free but
2.6× *more* expensive. **Shipping the NN to the GPU without Phase 2 delivers
nothing.**

Transient is *more* favourable to the GPU than DC: it needs the capacitances,
so it runs 3 backwards instead of 1, tripling the tensor share while the
stamping cost is unchanged.

## 4. Option B — ship the solver to the GPU

**Recommendation: no.** Three independent reasons.

1. **Amdahl forbids it.** 0.55 % of runtime. A solver that took *zero* time
   would make the 32×32 run 1.005× faster. There is no version of this that
   is worth the engineering or the accuracy risk.

2. **Circuit matrices are the worst case for GPU sparse LU.** MNA matrices are
   extremely sparse (~4–8 nnz/row), asymmetric and irregular. GPU sparse direct
   solvers win by finding dense supernodes to feed dense kernels; circuit
   matrices have tiny supernodes, so the GPU runs at a fraction of peak while
   paying transfer and launch latency. This is why production SPICE uses KLU
   (a CPU code specifically designed for circuit sparsity), not a GPU solver.
   §5 measures where fill-in starts to bite for the SRAM structure specifically.

3. **The cheap CPU win is unclaimed.** `_solve_mna` calls `spsolve` fresh every
   NR iteration — full symbolic analysis + numeric factorisation + solve. But
   **the sparsity pattern is identical across every NR iteration of every
   timestep**; only the values change. `splu` with a reused symbolic analysis
   is the standard answer and costs a few lines. Any argument for GPU solving
   has to beat *that* baseline, not the current one.

The one scenario that changes this verdict is arrays large enough that LU
fill-in on the bitline/wordline nodes dominates — see §5. That is a real
crossover, but it is far outside the sizes where the NN cost is the problem.

## 5. Where the solver *does* eventually become the bottleneck

The bitline and `vdd` nodes are the risk: every cell in a column touches
`bl_c`, and every cell touches `vdd`, so those nodes have degree ~2·rows and
~2·cells. High-degree nodes drive LU fill-in superlinearly. Measured on a
synthetic matrix with the array's connectivity (values randomised, diagonally
dominant), single-threaded:

| array | cells | N | nnz | `spsolve` | `splu` factor+solve | `splu` **solve only** | LU nnz | fill |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 8×8 | 64 | 178 | 1,124 | 0.66 ms | 0.65 ms | **0.027 ms** | 15,446 | 13.7× |
| 16×16 | 256 | 610 | 4,292 | 2.87 ms | 2.87 ms | **0.082 ms** | 61,446 | 14.3× |
| 32×32 | 1,024 | 2,242 | 16,772 | 67 ms | 67 ms | **2.2 ms** | 773,476 | 46.1× |
| 64×64 | 4,096 | 8,578 | 66,308 | 3.03 s | 6.78 s | **16.7 ms** | 10,858,454 | 163.8× |
| 96×96 | 9,216 | 19,010 | 148,612 | 34.9 s | 21.9 s | **56.0 ms** | 31,132,392 | 209.5× |

> **Read this table with care — it overstates the problem.** At 32×32 the
> synthetic matrix takes 67 ms per solve, but the *real* MNA at the same size
> measured 5.4 ms (0.22 s / 41 solves) — **the synthetic is ~12× pessimistic**,
> because randomised values defeat pivoting differently than real device
> conductances do. Treat the absolute times as an upper bound and the *shape*
> as the finding. A faithful large-array measurement needs the real assembled
> matrix, which Phase 1 (fast parse) makes cheap to obtain; do that before
> acting on this section.

Two things survive the caveat:

1. **There is a real crossover.** Fill-in grows 13.7× → 209.5×, and the solve
   grows far faster than `O(N)`. The solver is 0.55 % at 6144 devices, but it
   will not stay there. Somewhere past ~4k cells it becomes the dominant term.
2. **The headroom is refactorisation, not the GPU.** `splu`'s *solve-only* step
   is **30–600× cheaper** than a full `spsolve` (2.2 ms vs 67 ms at 32×32;
   56 ms vs 34.9 s at 96×96). The MNA sparsity pattern is **identical across
   every NR iteration** — only the values change. A solver that reuses the
   pivot order and refactorises numerically is the entire game here.

**Correction to a tempting shortcut:** "just use `splu` instead of `spsolve`"
does *not* capture this. The table shows `splu` factor+solve measuring the same
as `spsolve` (67.4 vs 67.2 ms at 32×32) — because the numeric factorisation,
not the symbolic analysis, is the expensive part, and scipy exposes no
refactorise-with-existing-pivots API. Capturing the 30–600× requires a solver
with a refactorisation entry point — **KLU**, which exists precisely for circuit
matrices and is what production SPICE uses. That is a CPU library, and it
reinforces §4 rather than weakening it: the answer to a slow circuit solve is
KLU, not CUDA.

## 6. The parse bug (free win, bit-identical)

Parse is 44 s at 6144 devices — as expensive as the solve, and it is not a
scaling law. `_MOSFETNNBase.__init__` calls

```python
state = torch.load(str(model_path_obj), weights_only=True, map_location="cpu")
```

**unconditionally**, and only *afterwards* consults `_SHARED_NN_MODULES` to
decide whether to build a module from it. When the module is already cached the
freshly deserialised `state` is discarded.

Measured by counting calls during an 8×8 parse:

```
parse=2.04s  nn_devices=384  torch.load calls=384 totalling 1.12s
```

**One `torch.load` per device — 55 % of parse time**, re-deserialising the same
3.6 MB file 384 times to throw 383 of them away. At 6144 devices that is ~22 GB
of pointless I/O and unpickling, ~18 s of the 44 s parse. `NormStats.load` is
re-read per device likewise (~1.3 ms each).

Fix: consult the cache key first, and only `torch.load` on a miss. Strictly
bit-identical (the weights are the same object either way), taking parse from
`O(devices × checkpoint)` to `O(devices + checkpoints)`.

> Note for whoever implements this: an isolated microbenchmark of `torch.load`
> on this file reports 15 ms/call, which would predict 93 s at 6144 devices —
> more than the entire measured parse. The in-situ cost is 2.9 ms. Trust the
> call-counting measurement, not the microbenchmark; the isolated loop does not
> reproduce the allocator and page-cache state of a real parse.

Secondary: the resolver prints one `[NN-resolver]` line per device — 6144 lines
of stdout for a 32×32 array. Summarise per (checkpoint, count).

## 7. Routing — what to build, in order

Two tracks over a shared base (**both** are in scope — §8):

```
Phase 0  confirm scaling on .tran            ─┐
Phase 1  parse fix          (bit-identical)   ├─ shared, do first
Phase 2  vectorise per-device Python          ─┘
                    │
         ┌──────────┴──────────┐
   Track B (§8)            Track A
   Phase 5 batched MC      Phase 3 GPU NN eval
                           Phase 4 KLU / solver hygiene
```

Ordered by measured payoff per unit of risk. Phases 1–2 are bit-identical and
ship default-on; Phase 3+ perturb float ordering and are gated. **Phase 5 is
recommended ahead of Phase 3** — better payoff-to-risk, see §8.

### Phase 0 — confirm the scaling law on the workloads we actually care about
Everything above is `.op` with `.ic` on every cell. Before building on it,
re-run the §2 profile for (a) a read/write `.tran` on a 16×16 array, and (b) an
array *without* `.ic`. Two things to check: does the solve count stay
size-independent, and does the bucket split hold. Transient should shift
*toward* the tensor bucket (3 backwards for the caps), which strengthens the
GPU case — but if the solve count grows with array size, the linear-cost
assumption behind every estimate in §3.4 is wrong and the routing needs
revisiting. Cheap, and it de-risks the rest.

### Phase 1 — parse fix (bit-identical, default-on)
Cache-first `torch.load` + `NormStats` reuse; collapse resolver logging.
**Measured headroom: 55 % of parse at 8×8, ~18 s of the 44 s at 32×32.**
Zero accuracy surface. Gate: existing suite must be byte-identical.

### Phase 2 — vectorise the per-device Python (bit-identical *by construction*, default-on)
This is the load-bearing phase and the one that unlocks everything else.

- **2a — batched denorm tail.** Replace the per-device `_unpack_eval` loop with
  a batched numpy path over the whole `(N, 13)` block: one D2H transfer, one
  vectorised denorm, one vectorised `_denorm_deriv`, one vectorised
  `_guard_gds`, one vectorised `_apply_vds_correction`.
  **Bit-identity is achievable but not automatic** — the existing scalar code
  is full of deliberate rounding choices (`np.sinh` over `math.sinh`, the
  un-regrouped `d·out_std·factor/in_std` association, `math.sqrt`). The
  vectorised form must reproduce each one elementwise, and a bit-exactness
  test against the scalar path is the acceptance criterion, not an afterthought.
  Any element that cannot be reproduced exactly demotes this to Phase 3.
- **2b — vectorised stamping.** Replace the per-device `lil_matrix` stamping
  with a batched COO assembly: accumulate `(rows, cols, vals)` arrays for all
  devices, then one `coo_matrix(...).tocsr()`. Summation order inside duplicate
  coordinates changes, so **this one is perturbing** — it belongs to Phase 3's
  gating discipline even though it lives here logically.
- **2c — cache the stacked group inputs** (§3.3b). `_geo_norm_t` and
  `_tech_code_tensor` are immutable per device, yet are re-stacked every NR
  iteration. Stack once per group, invalidate on group membership change.
  Bit-identical (same values, same order), and worth 23–384× on that step.
  Helps CPU as well as GPU; on GPU it removes N kernel launches per iteration.

**Expected: tail 7.2 s → ~0.7 s, stamp 11.6 s → ~1.2 s.** On its own,
~1.7× with no GPU at all.

### Phase 3 — GPU NN eval (perturbing, default-OFF behind a flag)
`PYCIRCUITSIM_NN_DEVICE=cuda`, default unset = CPU. Requires Phase 2a, or it
is slower than the CPU (§3.3). Build inputs on-device, single D2H of results.

**Expected with Phase 1+2: ~10× end-to-end on a 32×32 `.op`.**

**Accuracy discipline — non-negotiable, and this project has the scar tissue.**
A GPU GEMM reorders the reduction, so this is *perturbing* in exactly the sense
that `NN_BATCHED_EVAL=0` and `PYCIRCUITSIM_NN_FUSED_JAC` already document. The
memory record is explicit that OMP thread-count changes alone flipped complex
gates, and that CPU-vs-CUDA float lands different NR basins in bistable
circuits — **which is precisely what a 6T SRAM latch is.** Therefore:

- ships default-off; the 16-gate suite stays CPU-pinned and must remain
  byte-identical with the flag unset;
- promotion requires a full 16-gate strict re-gate *on GPU*, plus the
  `verify_complex_sram_snm` butterfly and the `force_ic` retention probe;
- results become GPU-model-dependent — a 4090 result need not match an A100.
  Any GPU-produced accuracy number must record the device, and GPU numbers
  never enter the /16 scoreboard without their own column
  (`docs/accuracy/methodology.md` §7 discipline).

### Phase 4 — solver hygiene (CPU, not GPU)
Small today (0.55 %) but §5 shows it does not stay small, and this is the
correct baseline before anyone re-opens the GPU-solver question.

- Free hygiene: drop the redundant second `tocsr()` in `_mna_residual_inf`
  (one per NR iteration), cache `get_node_map` / `get_nodes` (currently
  re-sorts the whole node list per call).
- **Refactorisation.** The 30–600× in §5 needs a solver with a
  refactorise-with-existing-pivots API. scipy has none — `splu` measures the
  same as `spsolve`. KLU is the right target. Scope it as its own investigation
  (binding choice, licence, build, and whether the numerics move) rather than
  folding it into this plan.
- Prerequisite: re-measure §5 on the **real** assembled matrix at 64×64+ before
  committing to any of it, since the synthetic overstates by ~12×.

### Phase 5 — batched Monte Carlo / yield (Track B) — see §8
Batch the *circuits*: batched MNA assembly + batched small dense LU +
per-circuit NR masking, for thousands of independent 6T cells. Depends on
Phase 2, not on Phase 3. **Recommended ahead of Phase 3** (§8).

### Explicitly NOT doing
- **GPU sparse LU / cuDSS.** §4. Revisit only if §5 shows fill-in dominating at
  a size we actually need, *and* only after Phase 4.
- **Multi-threaded CPU torch as the answer.** 192 cores is tempting, but
  thread-count changes are already a documented gate-flip source in this repo
  (the OMP-strict discipline exists for this). It has the same accuracy cost as
  the GPU with a fraction of the payoff.

## 8. Track B — Monte Carlo / yield (confirmed in scope)

**Target confirmed as _both_**: array-level simulation for characterisation
*and* many independent cells for SNM / yield. Phases 0–4 above are **Track A**
(one big array, one MNA system). Track B is the Monte Carlo workload, and it
has a different optimum — important because the GPU case there is *stronger*
than for Track A, not weaker.

**Why it is the better GPU fit.** Thousands of independent 6-device cells are
embarrassingly parallel and, critically, **identically structured**: every cell
has the same 15×15-ish MNA system with the same sparsity, differing only in
values. That is the case GPUs are actually good at — and it dodges every reason
§4 rejects a GPU solver, because the parallelism is across *circuits*, not
inside one irregular sparse matrix.

**What it needs that Track A does not build:**

- **Batch the circuits, not just the devices.** One `batch_eval` over
  `n_cells × 6` rows already works and needs no change — Track B gets the NN
  batching for free, and at far better batch sizes than a single array reaches.
- **Batched MNA assembly** — one `(n_cells, N, N)` tensor, or a blocked sparse
  form, instead of `n_cells` separate `lil_matrix` builds.
- **Batched small LU** — `torch.linalg.lu_factor` / `solve` on a stacked
  `(n_cells, N, N)`, which is a dense batched kernel and exactly what the GPU
  wants. At N≈15 dense is cheaper than sparse.
- **Per-circuit NR convergence bookkeeping** — cells converge at different
  iteration counts, so the loop needs a per-circuit active mask rather than one
  global "converged" flag. This is the main new control-flow work.

**Sequencing against Track A.** Phases 1 and 2 are shared and unblock both, so
they stay first regardless. After that the tracks are independent:

- Track A continues into Phase 3 (GPU NN eval) then Phase 4 (KLU).
- Track B is **Phase 5**, and it can start as soon as Phase 2 lands. It does
  *not* depend on Phase 3, though it inherits the same GPU accuracy discipline.

**Recommendation on ordering:** do Phases 0–2, then **Phase 5 before Phase 3**.
Track B has a better payoff-to-risk ratio — the parallelism is across
independent circuits, so it scales with the GPU rather than fighting Amdahl,
and a wrong answer in one Monte Carlo sample is far easier to detect than a
subtly shifted NR basin inside a 6144-device array.

**Accuracy note specific to Track B.** Monte Carlo over a bistable latch is the
*most* basin-sensitive workload in this repo. Two guards: seed the batched
solve identically to the scalar path and require per-cell agreement on a
sample, and keep a CPU scalar reference path runnable for any cell whose
result is flagged. An SNM distribution that is subtly wrong in the tail is the
failure mode that would not announce itself.

## 9. Summary

| | ship NN to GPU | ship solver to GPU |
| --- | --- | --- |
| share of runtime addressed | 48 % | 0.55 % |
| speedup alone, **measured** | **~1.0× (0.46× at 8×8)** | 1.005× (ceiling) |
| speedup with Python vectorised | **~7–10×** | 1.005× |
| batching available | yes, free (2 checkpoints) | n/a |
| accuracy risk | high (perturbing, bistable SRAM) | high, for no gain |
| verdict | **do it — but only after Phase 2** | **no** |

The NN is the right GPU target by two orders of magnitude. But the honest
headline is that **the biggest single win is not the GPU at all** — it is
deleting the per-device Python (Phases 1 and 2), which is worth ~1.7× on its
own, is bit-identical where it matters, needs no re-gate, and is the
precondition for the GPU being worth anything.
